# Decisions that constrain implementation

Rules already settled, with the reason for each. Most are enforced in code and
will fail a test or a config load if broken. **If a rule looks wrong or gets in
the way, raise it rather than working around it.** Reversing one is a normal
conversation; routing around one silently is not.

**Read #25 first.** The 2026-09-08 faculty-feedback pivot is the live project
direction. Earlier rows remain as history or as constraints on the appendix
trading comparison, but #25 supersedes them wherever the product direction
conflicts.

| # | Rule | Why | Enforced by |
|---|---|---|---|
| 1 | Walk-forward is **30/6/6, step 6** (42 months per fold): 14 equity folds, 4 crypto, 0 options | The validation window exists so thresholds are never chosen on the test window. 30 months still spans several regimes | `WalkForwardConfig` defaults |
| 2 | **No volume-derived features**, in the models or in B2's strategy rules. This covers **volume-weighted prices**, VWAP distance included | Backtests run on SIP, live runs on IEX at ~3% of the volume. The 2026-09-02 transfer test measured Spearman 0.57 against a pre-committed 0.70 bar and failed. A VWAP distance looks scale-free because it is a price, but the weights are volumes, and IEX's ~3% share is a different execution mix rather than a random sample | Review. Do not reintroduce |
| 3 | An `asset_class: option` config **may not carry a `walk_forward` block** | Options history begins 2024-01-18. 31 months, and one fold needs 42. Zero folds | `RunConfig.validate()` |
| 4 | **No options result row carries a Sharpe or drawdown** | Options makes a fill-feasibility claim, never a performance claim | Harness schema test |
| 5 | Options require `fill_model: sparse_bar`. **A missing bar is a no-trade interval, never a forward-filled price** | Filling an absent bar invents a fill that could not have happened | `RunConfig.validate()`, execution simulator test |
| 6 | The options universe is **point-in-time**: `universe_as_of(t)` | Selecting a contract because it turns out to have traded is look-ahead bias, and the most likely correctness bug here | `AlpacaProvider.list_contracts` |
| 7 | **RTH filter runs before any feature is computed.** Crypto uses `continuous` instead | 60% of SIP bars fall outside regular hours and behave differently. Options carry extended-hours bars too | `RunConfig.validate()`, pipeline |
| 8 | `feed` is **equities only** (`sip` or `iex`). Crypto and options must not set one | Alpaca versions its data APIs per asset class; sip/iex is an equities concept | `RunConfig.validate()` |
| 9 | Per-asset-class history floors: SIP 2016-06-10, IEX 2021-06-10, crypto 2021-06-10, options 2024-01-18 | Measured by API probe. Earlier dates return no bars | `DataConfig.history_floor()` |
| 10 | **Backtest on SIP, live paper on IEX** | Recent SIP is not entitled on the free tier (403) and SIP streaming returns 409 | `RunConfig.validate()` |
| 11 | **Paper endpoints only.** No live-money code path exists | Safety guardrail from the Responsible AI charter | `AlpacaProvider.__init__` rejects a non-paper host |
| 12 | Credentials come from the environment, never source. **Startup makes one authenticated call and aborts on non-200** | A check that credentials are non-empty is not a check. A key rotation once produced a full run of 403s that looked successful | `authenticate()`, guardrail test |
| 13 | **Every results row records** `asset_class`, `feed`, `fold_scheme`, `n_folds`, `config_hash` | The comparability caveat belongs in the data, not in prose around it | `RunConfig.provenance()`, schema test |
| 14 | The LLM reads the **decision log only** and never enters the trade decision path | It narrates decisions the deterministic engine already made. This is what keeps the system outside the provider's high-risk category | Grounding checker, ≥50-sample audit |
| 15 | **No market data, verification reports, or full decision logs in the repo.** Bounded sample fixtures only | Vendor terms prohibit redistribution, and a multi-year decision log approximates a price series | `tests/test_guardrails.py`, CI |
| 16 | Coverage validation: **do not assert exactly 78 bars/day**, flag days below 90%, exclude the first and last day of any fetch window | Post-filter counts legitimately fall short on a thin feed, and a window edge is not an outage | Pipeline validation |
| 17 | **SUPERSEDED as the project's primary metric by #25 (2026-09-08); the pre-registration itself stands and its result is reported as appendix evidence.** The primary metric was **locked**: annualised Sharpe, M2 versus B2, equities only | Prespecified before any model was trained. See `EVALUATION_PROTOCOL.md` | Guardrail test |
| 18 | **Test-window results have been seen (2026-09-04).** Every change to the system from here is post-hoc: it needs a decision-log entry and disclosure under the protocol's change rule | Tuning B2 or swapping the primary strategy until a number improves is specification searching. Selecting B2's parameters per fold **on the validation window** is the one change defensible on its own merits, since that is what the window is for | `build_strategy` will not promote a secondary strategy; `assert_gradeable` will not grade one |
| 19 | **`dist_high_78` excludes the current bar** (Donchian reading) | A window containing the bar's own high makes a breakout unreachable, because the close is bounded above by that high. The strategy fired on 0 of 859 bars until this was corrected | `features/core.py`, `tests/test_features.py` |
| 20 | **Cost stress re-prices, it does not refit.** The stressed run replays the test window with the same fitted models and the same threshold | Condition 3 asks whether an effect survives 2x costs. Refitting would change the signal-quality labels and answer a different question | `ExecutionConfig.cost_multiplier`, `tests/test_execution.py` |
| 21 | **EVALUATION_PROTOCOL.md Amendment 1 (2026-09-05).** §3 records that the bootstrap resamples common day indices; §5 records the realised correlation of 0.407 and the detection floor of 0.808, which falsify its assumed table | ΔSharpe is a difference of two Sharpes, and a Sharpe does not distribute over subtraction, so how the pairing is done had to be stated. §5's own text mandated the exposure measurement before its figures were quoted; making it invalidated them. Neither note changes the decision rule | The protocol header points at both; `tests/test_guardrails.py` still pins the constants |

| 22 | **A rubric-assisted LLM judge may verify soft prose claims, but is never the source of truth.** The deterministic check against the frozen evidence manifest is the gate. The judge may only **downgrade**: flag a claim unsupported or disputed and send it to human review. It may never clear a claim the deterministic check did not clear, and anything unsupported or disputed is blocked or queued for a person | A judge that can clear becomes the gate by the back door, and the project's central claim is that grounding is checked rather than asserted. Low temperature is not determinism, so a judge verdict is evidence about a claim, not a verdict on it. Its agreement with human labels is measured rather than assumed | PRD §5.11A AC: a claim failing the deterministic check stays blocked whatever the judge returns |

| 23 | **SUPERSEDED in framing by #25 (2026-09-08): the three families are kept, but as generators of varied decision records rather than as a user-facing menu. The per-strategy claim discipline below is unchanged and still binds.** Project Beta was a multi-strategy workbench. The user selects a strategy family at setup - momentum breakout, moving-average trend or mean reversion - and it runs the entire pipeline. Validation status and performance claims stay separate per strategy: a family may be described as *validated* only after passing the same pre-registered protocol in full (walk-forward, cost stress, leakage checks, ablation, failure analysis), and no claim may compare families to pick a winner. The course deliverable implements all three and validates one; MA trend and mean reversion are named follow-on validation candidates after the course unless schedule allows one to be pulled forward** | Strategy choice is a product capability and evidence is a per-strategy property; conflating them is how a toggle becomes an implied endorsement. Three families each hunting a positive result is three chances at one finding, which is the multiple-comparisons failure pre-registration exists to prevent. Today momentum is the only family that has run the protocol, and it returned `no_claim`, so **no family is currently validated** | PRD §5.3; `strategy.tier` in the config and its provenance; `assert_gradeable`; `build_strategy` refuses promotion; results-row schema test on `strategy` and `strategy_version` |

| 24 | **AMENDED by #25 (2026-09-08): the Week 8 gate is removed and both surfaces are core. Everything else below stands.** Two interaction surfaces. Decision-level interrogation is in the guaranteed core (PRD §5.11B): the user selects a decision, or a timestamp where none happened, and asks a bounded question answered from that decision's own stored fields. Cross-artifact natural-language analysis (§5.11A) stays optional behind the Week 8 manifest-grounding gate** | The per-decision surface needs no manifest: `grounding.py` already checks a text against one record and is tested, so the guarantee exists today. Making the product's only interaction depend on an optional layer would mean the workbench disappears if the layer is cut, which is not what the cut was for. The one new piece is a rule-state trace so a non-event can be explained; where it is absent the system says so rather than inferring a reason, because a guessed cause for a non-event is a fabricated claim about the system's own state | PRD §5.11B AC: answers pass `enforce_grounding` against the single record; a non-decision returns the failed rule condition or an explicit "not recorded"; a test asserts the inspector answers with no access to the manifest, so the §5.11A cut cannot silently disable it |

| 25 | **PIVOT, 2026-09-08, on faculty instruction. The centre of the project moves from trading-performance optimisation to an evidence-grounded inspector and agent over a simulated trading account.** Profitability is no longer a success criterion; **faithfulness, refusal rate and audit time** are the primary metrics. **Equities only: crypto and options are cut.** The §5.11A Week 8 gate is removed and both question tiers are core. Scope settled 2026-09-09 as the **middle** account layer: accounts, balances, positions, order history, confirmation records and simulated order placement through the existing execution simulator, with **no order book and no matching engine**. The three equity strategy families are kept as generators of varied decision records rather than as a user-facing menu. **M1 and M2 remain load-bearing**, because they produce the decisions, rejections, model scores and records the inspector must explain | The AI content of an AI-engineering capstone was sitting in two hand-written logistic regressions, which is conventional supervised learning. Moving the centre to the inspector puts the graded contribution where the modern-AI work is: tool calling, grounded answers, measured refusal and evaluation design. The `no_claim` result is not a failure to be recovered from but the measured reason the agent declines to rank strategies | Supersedes #17, #23 and #24 where they conflict. `Project_Outline.md` §13, `PROJECT_BETA_PRD.md`, and `Project-Beta-Private/papers_implement.md` carry the specification |

| 26 | **The inspector harness takes a pluggable answerer from its first implementation.** One interface, one question-and-record input, one answer-or-refusal output. `E0`, `E1`, `E2`, `Oracle` and `Full` all run through it, and `E3` plugs in unchanged if schedule allows. No system may reach the evaluation set by a private path | Five systems answer the same 200 cases, so the harness is a five-slot fixture from day one or it is a rewrite in Week 8. It is also the only way the comparison is honest: if `Full` is measured by different plumbing from `E1`, the gap between them is partly plumbing | The harness accepts an answerer at construction. A test runs the full evaluation with a stub answerer and with `E0`, asserting the same code path. Adding a system must require no harness change |

| 27 | **Retrieval is separable from answer generation.** Which records reach the prompt is decided by a component the answering path calls, never inside it. The harness can therefore supply records directly (**Oracle-record**), let the system retrieve (**Default**), or withhold them entirely (**No-record**) | These three modes separate retrieval failure from grounding failure from refusal miscalibration, which the current metric set collapses into one number. If retrieval is baked into the answering service the ablation cannot run at all, and the fix is a refactor of the component the whole project rests on | The answering path takes retrieved evidence as an argument. A test runs one question in all three modes. No-record must produce a refusal, asserted rather than assumed |

| 28 | **A `DecisionRecord` carrying a fitted threshold also carries the provenance that selected it**: the fold identity and the validation window, alongside `model_version` | The signal-quality threshold is chosen per validation window (`models/signal_quality.py`), so it is a fitted quantity that varies across folds, not a constant. An answer citing "below the 0.55 threshold" is ungrounded unless the record says which window produced 0.55. Cheapest to add before records are generated at scale, and it is a grounding correctness bug if it is missed | The record schema requires the fields wherever a threshold appears. A test asserts an answer citing a threshold also cites its window. `PROJECT_BETA_PRD.md` §5 carries the fields |
