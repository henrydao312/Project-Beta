# Decisions that constrain implementation

These are the decisions we use when building and reviewing the project. If one
needs to change, discuss it and record the change here. The last column names
the relevant implementation or acceptance check; some inspector checks are still
planned.

Read #25 first. The 2026-09-08 pivot after faculty feedback is the current
direction. Earlier rows are either history, or constraints on the trading
comparison that is now appendix evidence. #25 takes precedence wherever they
conflict. #29 records the team update and current M2 responsibilities.

| # | Rule | Why | Enforced by |
|---|---|---|---|
| 1 | Walk-forward is 30/6/6, step 6 (42 months per fold): 14 equity folds, 4 crypto, 0 options | The validation window keeps threshold selection out of the test data. A 30-month training window covers several market regimes | `WalkForwardConfig` defaults |
| 2 | **No volume-derived features**, in the models or in B2's rules. Volume-weighted prices count, VWAP distance included | Backtests run on SIP, live runs on IEX, which carries about 3% of the volume. The transfer test on 2026-09-02 came back at Spearman 0.57 against a 0.70 bar fixed before the run. VWAP distance looks scale-free because it is a price, but its weights are volumes, and 3% of the tape is a different mix of executions rather than a sample of the whole | Review. Do not reintroduce |
| 3 | An `asset_class: option` config may not carry a `walk_forward` block | Options history starts 2024-01-18. At the original feasibility check, that gave us 31 months of history; one fold needs 42 | `RunConfig.validate()` |
| 4 | No options result row carries a Sharpe or a drawdown | Options supports a fill-feasibility claim. There is no walk-forward result behind it | Harness schema test |
| 5 | Options require `fill_model: sparse_bar`. A missing bar is a no-trade interval, never a forward-filled price | Filling an absent bar invents a trade that could not have happened | `RunConfig.validate()`, execution simulator test |
| 6 | The options universe is point-in-time: `universe_as_of(t)` | Choosing a contract because it turned out to have traded is look-ahead bias, so contract selection must use only information available at the time | `AlpacaProvider.list_contracts` |
| 7 | The RTH filter runs before any feature is computed. Crypto uses `continuous` instead | About 60% of the SIP tape falls outside regular hours and behaves differently. Options carry extended-hours bars too | `RunConfig.validate()`, pipeline |
| 8 | `feed` is equities only (`sip` or `iex`). Crypto and options must not set one | Alpaca versions its data APIs per asset class, and sip/iex only means something for equities | `RunConfig.validate()` |
| 9 | History floors per asset class: SIP 2016-06-10, IEX 2021-06-10, crypto 2021-06-10, options 2024-01-18 | Measured by API probes. Earlier dates returned no bars | `DataConfig.history_floor()` |
| 10 | Backtest on SIP, live paper on IEX | Recent SIP is not entitled on the free tier (403), and SIP streaming returns 409 | `RunConfig.validate()` |
| 11 | Paper endpoints only. No live-money code path exists | The Responsible AI charter limits the project to paper trading | `AlpacaProvider.__init__` rejects a non-paper host |
| 12 | Credentials come from the environment, never from source, and startup makes one authenticated call and aborts on a non-200 | A key rotation once left a run returning 403s while appearing successful. Checking for non-empty variables did not catch invalid credentials | `authenticate()`, guardrail test |
| 13 | Every results row records `asset_class`, `feed`, `fold_scheme`, `n_folds`, `config_hash` | Numbers get copied into slides and write-ups. The caveat has to travel in the row rather than in the paragraph around it | `RunConfig.provenance()`, schema test |
| 14 | Updated by #25: the LLM answers from decision records, account records and permitted tool results. It never chooses trades. User-directed simulated orders require confirmation and tool-layer authorization | The inspector needs account evidence as well as decision logs. Trade selection remains with deterministic rules or the user | Grounding checker, 50-sample audit or larger |
| 15 | No market data, verification reports or full decision logs in the repo. Bounded sample fixtures only | The repository excludes licensed market data. A full decision log can also reconstruct a price series | `tests/test_guardrails.py`, CI |
| 16 | Coverage validation does not assert exactly 78 bars a day. Flag days under 90%, and drop the first and last day of any fetch window | Post-filter counts fall short legitimately on a thin feed, and a window edge is not an outage | Pipeline validation |
| 17 | Superseded as the primary metric by #25 on 2026-09-08. The pre-registration itself stands, and its result is reported as appendix evidence. The metric was locked as annualised Sharpe, M2 against B2, equities only | Fixed before any model was trained. See `EVALUATION_PROTOCOL.md` | Guardrail test |
| 18 | Test-window results have been seen, as of 2026-09-04. Every change from here is post-hoc and needs a decision-log entry and disclosure under the protocol's change rule | Tuning B2, or swapping the primary strategy until a number improves, is specification searching. Choosing B2's parameters per fold on the validation window is the one change that stands on its own, because that is what the window is for | `build_strategy` will not promote a secondary strategy; `assert_gradeable` will not grade one |
| 19 | `dist_high_78` excludes the current bar, which is the Donchian reading | Until this was corrected the strategy fired on 0 of 859 bars. A window that contains the bar's own high puts the breakout out of reach, since the close cannot exceed it | `features/core.py`, `tests/test_features.py` |
| 20 | Cost stress re-prices, it does not refit. The stressed run replays the test window with the same fitted models and the same threshold | Condition 3 asks whether the effect survives 2x costs. Refitting changes the signal-quality labels, and then we are answering a different question | `ExecutionConfig.cost_multiplier`, `tests/test_execution.py` |
| 21 | `EVALUATION_PROTOCOL.md` Amendment 1, 2026-09-05. §3 records that the bootstrap resamples common day indices. §5 records the realised correlation of 0.407 and the detection floor of 0.808, which invalidate the assumptions behind the original table | ΔSharpe is a difference of two Sharpes rather than the Sharpe of a difference, so how the pairing works had to be written down. §5 required the exposure measurement before its figures could be quoted, and running it invalidated them. Neither note changes the decision rule | The protocol header points at both; `tests/test_guardrails.py` still pins the constants |
| 22 | A rubric-assisted LLM judge may review prose only after deterministic evidence checks pass. It may flag an answer as unsupported or disputed, but may never clear a failed check. Flagged answers stay blocked or go to human review | The judge can help identify problems in prose, but its output is not proof. We measure its agreement with human labels | PRD §8 and §9: failed grounding checks remain blocked regardless of the judge |
| 23 | Superseded in product framing by #25 on 2026-09-08. Momentum breakout, moving-average trend and mean reversion now generate varied records. Validation claims remain separate for each family. A family may be called validated only after passing the full pre-registered protocol: walk-forward, cost stress, leakage checks, ablation and failure analysis. We do not compare families to select a winner | Testing several families and reporting only the best would undermine the pre-registration. Momentum returned `no_claim`; no family is currently validated. The former plan to validate one family is not a promise of a positive result | Outline §4 and §10; `strategy.tier`; `assert_gradeable`; `build_strategy`; results-row strategy provenance |
| 24 | Amended by #25 on 2026-09-08: single-record inspection and cross-record analysis are both core. There is no Week 8 gate. A single-record question uses that record alone. A non-decision explanation requires a rule-state trace or an explicit "not recorded" response | The single-record inspector should work independently of cross-record retrieval. If a trace is missing, we cannot reconstruct why nothing happened from the outcome alone | PRD §5 and §8; `enforce_grounding`; acceptance tests for missing traces and inspection without a manifest |
| 25 | **Pivot, 2026-09-08, after faculty feedback.** The project is an evidence-grounded inspector and agent over a simulated trading account. Profitability is no longer a success criterion. We measure faithfulness, correct and false refusal, contradictions and audit time. Equities only; crypto and options are out of capstone scope. Both question tiers are core. The account scope settled on 2026-09-09 includes accounts, balances, positions, order history, confirmation records and simulated order placement through the existing execution simulator. No order book or matching engine. The three strategy families, M1 and M2 generate the records the inspector explains | Faculty feedback put the AI-engineering work on the inspector: tool use, grounded answers and evaluation. The trading comparison remains appendix evidence, including its `no_claim` result. The inspector refuses strategy-ranking requests under the project policy | Supersedes earlier product framing, including #14, #17, #23 and #24. Outline §4, §8 and §9; PRD §5–§10 |
| 26 | The inspector harness accepts an answerer through one interface: a question and evidence in, an answer or refusal out. E0, E1, E2, E3, Oracle and Full use the same evaluation path. E3 is part of the current M2 baseline plan; see #29 | A shared interface keeps the comparison consistent and lets us add or replace an answerer without rewriting the harness | The harness accepts an answerer at construction. A test runs a stub and E0 through the same evaluation path. Adding a system requires no harness change |
| 27 | Retrieval stays separate from answer generation. The answerer takes evidence as an argument. The harness can supply the required records directly (Oracle-record), use system retrieval (Default), or withhold evidence (No-record) | These modes help distinguish retrieval errors from errors in answering or refusing. If retrieval happens inside the answerer, we cannot control the evidence independently | PRD §9. A test runs the same question in all three modes. When the necessary evidence is withheld, No-record must refuse |
| 28 | A `DecisionRecord` containing a fitted threshold also records the fold and validation window that selected it, alongside `model_version` | M2 thresholds vary across validation windows. An explanation citing a threshold must identify the window it came from so the value can be checked | PRD §5. Require provenance wherever a fitted threshold appears, and test that an answer citing a threshold also cites its window |
